### WP-05 — Уведомление вкладок об изменениях хранилищ (P2)

- **Доказательства:** CONFIRMED по пути кода. `cartStore.ts:172-185` кэширует состояние в памяти модуля, слушателя `storage` в `src` нет. Тот же шаблон в favourites, compare, account и city. Вторая вкладка работает с устаревшим кэшем, и её следующая запись перезаписывает чужую правку.
- **Объём:** подписка каждого стора на событие `storage` для своего ключа: сброс кэша, повторное чтение через существующий парсер, уведомление подписчиков. Ключи и парсеры `goodcall.*.v1` не меняются. `goodcall.lastOrder.v1` живёт в sessionStorage одной вкладки и не затрагивается.
- **Важное ограничение:** событие `storage` только уведомляет **другие** вкладки. Оно не даёт атомарности, транзакций и слияния конкурентных правок.
- **Приёмка:**
  1. После **последовательных** изменений в двух вкладках обе показывают актуальное состояние; восстановление из `*.v1` и подписчики работают корректно.
  2. Собственная запись вкладки не порождает в ней `storage`-событие; локальные изменения идут через текущий контракт store/subscribe.
  3. **Одновременные конфликтующие** записи: известное ограничение last-write-wins. Явно задокументировать его. Настоящее разрешение конфликтов — отдельное продуктово-техническое решение без нового persistence-движка.
- **Исключено:** BroadcastChannel, service worker, транзакционная архитектура, новый framework.
- **Проверка (будущая):** детерминированные Node-тесты в стиле `compare-store` — последовательные события, удаление ключа, неизвестная или повреждённая версия, восстановление из хранения. Конкурентный сценарий описать отдельно. Плюс `cart`, `favorites`, `account`. Это предпосылка миграции на RTK (D-13).

## 4. Зависимости и риск-гейты

- **Хранилище браузера:** ключи `goodcall.{cart,favorites,compare,account,city}.v1` (localStorage) и `goodcall.lastOrder.v1` (sessionStorage) сохраняют формат; любое изменение формы — через новую версию с миграцией.
- **Supabase/DaData:** только публичное чтение каталога; токен DaData публичен по природе (AUD-14 EXTERNAL_BLOCKED — ограничения домена и квоты на стороне DaData); живые API в verify не проверяются (mock).
- **GitHub Pages / HashRouter:** base path только в `vite.config.ts`; code splitting и новые маршруты проверяются прямым входом и F5.
- **Происхождение данных, изображений и текстов:** не выдумывать медиа, статьи, цены, сроки и гарантии.
- **A11y/адаптив:** сохранять фокус, `aria-*`, reduced motion (GC-R63 выполнен; AUD-13 — мелочь при следующем касании контролов).
- **Правдивость:** вымышленные магазины в реальных ТЦ, телефон, Privacy; реальных продаж и платежей нет.
- **Карта:** условия, квоты и приватность провайдера до любой зависимости.
- **Принятые визуалы:** закрытые milestones и Quality A–G не переоткрываются; Q-03 и исправленный срез Q-08 закрыты.

## 6. Политика приёмки

1. До реализации: каждый bounded milestone фиксирует объём, исключения, зависимости, риски, тесты и визуальные гейты и получает явное утверждение пользователя.
2. После реализации: `npm run verify` (или релевантные гейты) и `typecheck`/`lint`/`lint:styles`/`format:check`/`build`; защищённые pixel diff остаются 0, если изменение их не касается по решению.
3. Изменения с визуальной стороной требуют сравнения с эталоном и **USER VISUAL PASS** до закрытия. Зелёная сборка — не визуальное одобрение.
4. Изменения хранилища — с совместимостью `*.v1` или миграцией и тестом восстановления; изменения Privacy следуют за реальными изменениями хранения.
5. Улучшения производительности заявлять только по замеру до и после.
